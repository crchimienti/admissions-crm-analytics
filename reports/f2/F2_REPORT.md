## Event order and contract (v1.2.2-f2)

The approved stage_events specification (key record_id + seq; required record_id, seq, stage, entered_at, event_kind; optional exited_at, changed_by_type; seq orders equal timestamps) is mapped column by column in docs/canonical_schema.md §11.3. The contract becomes crm-canonical/0.1.1, an additive revision: an optional seq keeps the source order and is unique per record and consistent with occurred_at (C08). Without seq, events of one record with the same occurred_at have an indeterminate order (C09); it is never resolved by stage, event_id or file position (the event_id tie-break that v1.2.1-f2 used inside time_in_stage was removed). Only time_in_stage depends on order and is then not_available with reason ORD. Regressions, reopens, entry counts and first entries do not depend on order: tests/test_canonical_event_order.py checks them with simultaneous events, shuffled rows and renamed ids. exited_at and changed_by_type are not represented (§11.3). The admissions CSV gives no order, so its mapping still emits crm-canonical/0.1 datasets without seq, which 0.1.1 accepts.

current_status is not the approved status = open/won/lost: it keeps the profile operational statuses (new, working, iloc_sequence, nurture, closed_won, closed_lost). The outcome is derived from current_stage only (closed_won → won, closed_lost → lost, else open), so a nurture record is lost, never a fourth outcome; checked on the fixture and on the generated data (docs §11.2).
